1. まず全体像（このプロジェクトの3つの顔）

このプロジェクトは、見た目は別々ですが、3つの道具が組み合わさってできています。

# 道具 誰が使う 何をする
① 学習アプリ（index.html） 学生 過去問・予想問題を解いて学ぶ
② 管理画面（admin.html） 先生（あなた） 学生の報告を確認し、問題を「確認済み」にする
③ 弾幕（danmaku_*.html） 授業中の学生＋先生 授業スライドにコメントを流す

データの置き場所は2か所だけ

むずかしく見えますが、データのありかは実は2種類です。

　【1】GitHub（ギットハブ）… ファイルの保管庫 ＆ 公開サーバー
　　　・問題データ（jsonlファイル2つ）
　　　・画像（FUTURE/ と JPPE_norm/）
　　　・アプリ本体（index.html, admin.html, 弾幕ページ）
　　　　→ これらは「GitHub Pages」という機能で、そのままWebサイトとして公開されている

　【2】Supabase（スーパベース）… クラウドのデータベース（2プロジェクト）
　　　・本体用：学生の「報告」と「検証済み」の記録、管理画面のログイン
　　　・弾幕用：授業中のコメント（※こちらは別プロジェクト）

ポイント： - 問題そのもの（問題文・選択肢・正解・解説・画像）は GitHub の中のファイルにあります。Supabaseには入っていません。 - 学生の声（報告・「妥当」評価）と検証の記録だけが Supabase に貯まります。 - だから「問題を直す」＝GitHubのファイルを直す、「学生の報告を見る」＝Supabaseを見る（＝管理画面を開く）、という住み分けになっています。

3. 学生用アプリ（index.html）

学生が実際に解く画面です。学生向けの詳しい使い方は別冊「衛生薬学アプリ 使い方ガイド（PDF）」にまとめてあります。ここでは管理者として知っておく要点だけ。

  • できること：分野・国試の回・授業回・予想/過去問で範囲を選んで出題、即採点と解説、苦手問題のみ復習、検索、進捗確認、問題への「報告」。
  • ログイン不要：学生は匿名で使えます。学習の記録（正答率など）はその学生の端末のブラウザの中だけに保存され、サーバーには送られません。
  • データの読み込み元：開くと future_questions.jsonl と hygiene_with_images_v4.jsonl を読み込み、画像は FUTURE/ や JPPE_norm/ から表示します。つまり、これらのファイルをGitHubで更新すれば、学生のアプリにも反映されます（→ 8章）。
  • 学生が送れるもの：各問題の「👍 OK（妥当）」「⚠ 気になる点を報告」。これだけがSupabaseに送られ、あなたの管理画面に届きます。

4. 管理画面（admin.html）で学生の声に対応する

学生からの報告を確認し、対応し、問題を「確認済み」にしていく、先生専用の画面です。

4-1. 開き方とログイン

  1. ブラウザで https://tmatsuka-art.github.io/eisei_yakugaku/admin.html を開きます。 - ⚠ 必ずこの公開URLから開いてください。 パソコンに保存した admin.html を単独でダブルクリックして開くと、問題データ（jsonl）を読み込めず、問題の中身が「見つかりません」になることがあります。
  2. 「ログイン」画面が出ます。メールアドレスとパスワードを入れて「ログイン」。 - これはSupabaseに登録した管理者アカウントです（あなたが設定したもの）。 - 失敗すると赤字で「ログイン失敗」と出ます。
  3. 一度ログインすれば、しばらくはログインしたままになります。やめるときは右上の「ログアウト」。

4-2. 5つのタブ

画面の上に5つのタブがあり、右の (数字) は件数です。

タブ 表示されるもの できること
⚠ 未対応の報告 まだ対応していない報告 内容確認 → 対応済みにする／修正依頼コピー／検証済みにする
✓ 対応済み 対応を終えた報告 内容確認／未対応に戻す
全報告 すべての報告 上記の操作
📋 検証履歴 確認済みの問題一覧 検証の解除／学生人気の問題を「公式検証に格上げ」
🔧 問題を直す 問題の検索ボックス 報告が無くても、任意の問題を探して修正依頼を作る

4-3. 報告に対応する（基本の流れ）

「⚠ 未対応の報告」タブで、問題ごとに報告カードが並びます。カードには問題の中身と、各報告の種別（「正解が違うと思う」「選択肢が不適切」「問題文がわかりにくい」「図表がおかしい」「解説が不十分」「その他」）、日時、学生の匿名ID、コメントが出ます。

対応の手順： 1. 報告を読む。 2. 直す必要があれば、後述の「📋 Claudeに修正依頼をコピー」で直す（→ 5章）。 3. 「対応の結果」をプルダウンから選ぶ： - fixed（修正した）／not_an_error（誤りではなかった）／wontfix（今回は直さない）／duplicate（重複） 4. 必要ならメモを書いて、「✓ 対応済みにする」を押す。 5. これで「対応済み」タブに移ります。間違えたら「↶ 未対応に戻す」で戻せます。

知っておくと安心な自動動作：対応の結果に fixed を選ぶと、その問題は自動で「検証済み（ヒトの目で確認済み）」にもなります。「直した＝確認した」とみなす仕組みです。 ただし、その後「未対応に戻す」をしても、いったん付いた検証済みは自動では外れません。外したいときは下記の検証ボタンで解除してください。

4-4. 「検証済み」を管理する

「検証済み」は、その問題を人の目で確認した／妥当だ、という印です。問題カードや検証履歴に、次の3つのバッジで状態が出ます。

バッジ 意味
✓ ヒトの目で確認済み（緑） 先生が確認した。いちばん信頼できる状態
🤖 AI作成・検証募集中（青） まだ誰も確認していない
👥 学生が「妥当」と評価のみ（オレンジ） 先生の確認はまだだが、学生が「妥当」と投票している

操作： - 問題カードの「☐ 検証済みにする」で確認済みにできます（即実行）。「✓ 検証済み（解除）」で外せます（確認あり）。 - 「📋 検証履歴」タブで、学生人気だけの問題（オレンジ）を「☑ 公式検証に格上げ」で先生のお墨付き（緑）に引き上げられます。

4-5. 「📋 Claudeに修正依頼をコピー」

このボタンは問題の中身を自動でコピーしてくれるので、手で書き写す必要がありません。コピーされた文章をClaude（このAIアシスタント）に貼り付けて「直して」と頼むのが基本の流れです。

  • 報告カードの中のボタン → 学生の報告内容＋問題の現在の中身＋「直して」という依頼文がコピーされます。
  • 「🔧 問題を直す」タブのボタン → そのカードの「どう直したいか」の入力欄に書いた指示も一緒にコピーされます。さらに、過去問の改題ルール（IDは変えない・タイトルに「（改）」を付ける等）も自動で付きます。

このボタンは依頼文を作るだけで、問題ファイルは書き換えません。実際の修正はClaudeが行います。

4-6. 毎朝の自動まとめ（GitHub Issue ダイジェスト）

毎朝8時（日本時間）に、過去24時間に届いた学生の報告を自動でまとめ、GitHubの「Issue（イシュー）」として1件作成する仕組みが動いています（メールではありません）。

  • GitHubリポジトリ tmatsuka-art/eisei_yakugaku の「Issues」タブを見ると、📋 学生報告ダイジェスト 2026/MM/DD（N件） のような項目が並びます。
  • 中身は、報告のあった問題・件数・種別・コメントの一覧と、管理画面へのリンク。
  • これを見れば、毎朝「昨日どんな報告が来たか」をまとめて把握できます。報告が0件の日はIssueは作られません。

5. 問題を直す・追加する

問題の中身を直すのは、あなたがClaude（AI）に頼み、Claudeがファイルを書き換えるという二人三脚で行います。あなたが直接ファイルを編集する必要はありません。

5-1. 直すきっかけは2通り

(a) 学生の報告から直す 1. 管理画面で報告を開く。 2. 「📋 Claudeに修正依頼をコピー」を押す。 3. Claudeに貼り付けて「直して」と頼む。 4. Claudeが該当ファイルを修正し、保存（コミット＆プッシュ）。 5. 管理画面でその報告を「対応済み（fixed）」にする。

(b) 自分で気づいて直す - Claudeに直接「F856の選択肢3を直して」のように頼むだけでもOK。問題番号と直したい点が分かれば十分です。 - きちんと依頼したいときは「🔧 問題を直す」タブで対象を検索し、指示を書いてコピー → Claudeへ。

5-2. まとめて点検する「AIレビュー」（モードA / B / C）

個別の修正とは別に、問題を10〜20問単位でまとめて点検・改善する作業があります。複数の専門の係（コアカリ係・過去問係・事実確認係・品質係など最大7係）が並列で点検し、見つかった改善案を後述のTierに仕分けます。

頼み方は3モード。ふだんは何も言わずモードAです。

モード あなたの言い方 違い
🟢 モードA（標準） 「次のバッチやって」 安全な変更は自動、重要な変更は確認を求められる（判断は1バッチ3〜5回程度）
🟡 モードB（高速） 「モードBで頼む」 表現の磨き込みも自動。確認は重要案件だけ
🔴 モードC（背景） 「モードCで頼む」 全部処理して、重要案件だけ後でまとめて判断

5-3. 何を確認させられる？（Tier 1・2・3）

改善案は重要度で3段階に仕分けられます。あなたが判断を求められるのは Tier 2 と Tier 3 だけです。

段階 内容 あなたの関与
Tier 1 解説の追記、分類コードの軽微な修正、誤字直しなど なし（自動反映・事後報告のみ）
Tier 2 攪乱肢の表現改善、絶対化表現の除去、正答位置の調整など 1回（「全部OK」か「この番号は却下」）
Tier 3 問題文の全面書き換え、削除、正解そのものの変更など 1問ずつ確認

迷ったら上の段階に上げる（＝確認を求める）ルールにしています。「勝手に直された」を防ぐためです。

5-4. 安全のしくみ（失敗してもやり直せる）

  • バックアップを必ず取る：jsonlを直す前に、Claudeは future_questions.jsonl.bak_pre_○○_日付 のような控えを作ります。名前を見れば「いつ・何の作業の前か」が分かります。
  • 直接いきなり編集しない：必ず控えを取ってから。これはCLAUDE.mdに明記された鉄則です。
  • 1つの修正＝1つの記録：変更はGitHubの履歴（コミット）に1件ずつ残るので、後から「いつ何を直したか」をたどれ、必要なら戻せます。
  • 承認した分だけ反映：AIレビューでは、承認された内容をいったん決定ファイル（decisions）に貯め、専用スクリプトがまとめて反映します。Claudeが思いつきで書き換えることはありません。

5-5. 問題をまとめて追加・分類する

過去には、問題をまとめて追加したり、授業回（lecture_map.json）へ割り当て直したりする作業も行ってきました（_work/ フォルダのスクリプト群がその痕跡）。

⚠ 大事な前提：問題に元から付いている分類ラベルは3〜4割が誤りであることが分かっています。そのためラベルを鵜呑みにせず、問題の中身を読んで1問ずつ判定するのが、このプロジェクトで確立したやり方です。新しく分類・追加するときは、Claudeにもこの方針で進めてもらってください。

6. データとファイルの地図

6-1. 「jsonl」って何？

.jsonl は 1行に1問が入ったテキストファイルです。各行が「項目名: 中身」の集まり（JSON形式）になっていて、Excelの表を縦に積んだようなイメージです。日本語が含まれるので、メモ帳で開くと文字化けすることがあります。直接いじらず、Claudeに頼んで編集するのが安全です。

6-2. 2つの問題ファイル

① future_questions.jsonl（予想問題 約1,408問・F001〜）

1問に含まれる主な項目：

項目 中身
problem_id 問題の背番号（予想問題は必ず F で始まる）
problem_text 問題文
choices 選択肢（図問題は ['IMAGES'] という目印）
answer 正答の番号（複数選択もあり）
comment 解説
new_corecurri_code 新コアカリ（令和4年改訂）の分類コード
corecurri_code 旧コアカリのコード
assets 図ファイルへのパス（図なしは空）
lecture 関連 / lecture_map.json どの授業回で出すか
ai_review AIレビューの履歴。この項目が無い問題＝まだ点検していない目印

② hygiene_with_images_v4.jsonl（過去問 648問・97〜111回）

項目はほぼ共通ですが、過去問ならでは： - problem_id は 回＋問番号の6桁（例 097016 ＝ 第97回・問16） - year は国試の回数（97〜111。予想問題は 0） - display_title は「第97回 衛生 問16」のような表示名 - 図のある問題は189問。assets が JPPE_norm/JPPE097/097123.png のように画像を指す

6-3. lecture_map.json（授業回の割り当て表）

「どの問題を、どの科目の第何回で出すか」を決める表です。学習アプリの「授業回別」表示の土台になります。

  • 3科目（衛I＝衛生化学I／衛II＝衛生化学II／公衆＝公衆衛生学）に分かれる
  • 各科目の中に授業回（1, 2, 3…）があり、回ごとにテーマと問題IDのリストが入る
  • 問題を授業から外したいときは、この表からIDを抜きます（jsonlの問題自体は残る）

6-4. 画像の置き場所

種類 場所
予想問題の図 FUTURE/ フォルダ（ファイル名＝problem_id、例 F002.png）
過去問の図 JPPE_norm/JPPE097〜JPPE111（回ごとのフォルダ）

画像はすべてGitHubの中にあります。Supabaseには置いていません。

6-5. by_subcat_md/（分野別の読みやすい問題集）

jsonl（機械向け）の中身を、分野ごとに人が読みやすく書き出したMarkdown（49ファイル）です。点検や印刷に使えます。これは元データ（jsonl）から作り直せる「派生物」なので、ここを直しても本体には反映されません。直すのは必ずjsonl側です。

6-6. Supabase（クラウドのデータベース）

本体のSupabaseプロジェクト（gmkrsgqgndlrabiicvkh.supabase.co）には、2つの表だけがあります。

表 中身
question_feedback 学生の「👍 妥当」評価と「⚠ 報告」。報告には種別・コメント・日時・匿名IDが入る。対応すると先生のメモや結果も追記される
question_verifications 「検証済み」の記録（問題ID・検証日時・手動か報告経由か・メモ）

そのほか、ログイン認証（管理画面用）と、毎朝のダイジェスト自動作成（4-6）もここで動いています。

6-7. 控え・記録ファイルの見分け方

種類 例 何か
バックアップ *.bak_pre_○○_日付 作業前の控え。普段触らない。新しい日付ほど最近
レビュー進捗 ai_review_log_第9回.md 等 どの問題を点検したかのチェック表
引き継ぎメモ HANDOFF_2026-06-10.md 等 前回作業の引き継ぎ。新しい日付のものが最新
経緯まとめ 検証経過まとめ.md、新コアカリ分類案.md これまでの方針・分類ルール

新しいセッションでClaudeに作業を頼むときは、「最新のHANDOFFを読んでから始めて」と言うと、前回の続きをスムーズに引き継げます。

7. 弾幕機能（授業中のコメント表示）

授業スライドの上に、学生がスマホから送ったコメントを、ニコニコ動画のように右から左へ流す機能です。匿名なので学生が気軽に反応・質問でき、大教室でも双方向のやりとりが生まれます。

⚠ 弾幕のデータは、学習アプリとは別のSupabaseプロジェクト（eisei-quiz-live）の danmaku_comments という表に貯まります。学習アプリの報告とは混ざりません。

7-1. 3つのページの役割

ページ 役割 開き方
danmaku_post.html 学生が投稿する画面 スマホで …/danmaku_post.html（QRから自動で開ける）
danmaku_screen.html コメントを流す投影画面 OBS用は …/danmaku_screen.html?transparent=1
弾幕デモ.html 練習用（ネット不要、その場で試せる） ファイルを直接開く

部屋（room）：授業ごとにコメントを分けたいときは、URLに ?room=授業名 を付けます（投稿側・表示側で同じ名前にする）。投影画面のQRコードは自動で同じ部屋に紐づくので、学生がQRを読めば自動的に同じ部屋に入ります。

7-2. 授業当日の流れ

OBS（無料の画面合成ソフト）で「PowerPointの画面」と「透明な弾幕ページ」を2枚重ねて投影します。

  1. PowerPointを「ウィンドウ表示のスライドショー」で開く（スライドショーの設定 →「出席者として閲覧する（ウィンドウ表示）」）。送りは →キー / Page Down / ホイール。
  2. OBSを起動し、弾幕が上・PowerPointが下の重ね順、右下にQRが出ているか確認。
  3. 投影：教室なら「全画面プロジェクター」、Zoomなら「仮想カメラ開始」→ ZoomでOBS Virtual Cameraを選ぶ。
  4. 学生に投稿してもらう：QRを読んでもらう。投稿は3秒に1回まで。
  5. 終了：OBSの全画面/仮想カメラを止め、PowerPointを Esc で終了。

弾幕が出ない＝故障とは限りません。 弾幕は「開いた後に届いた新しいコメント」を流します。起動直後に直近のコメントを少し流したあとは、新しい投稿が来るまで画面はQRだけになります（正常）。出ないときは、まず投稿側と表示側の部屋(room)が一致しているかを確認してください。

7-3. OBS設定の要点

詳しくは 弾幕_OBS設定ガイド.md と 弾幕_授業当日の操作手順.md にあります。要点は： - OBSでブラウザソースを追加し、URLに …/danmaku_screen.html?transparent=1 を指定（幅1920・高さ1080）。 - ?transparent=1 を付けると弾幕ページの背景が透明になり、下のPowerPointが透けます（クロマキー不要）。 - もし弾幕の背景が黒くてスライドが隠れるときは、URL末尾の ?transparent=1 が付いているかを確認。

補足：当日手順メモには「通信: SUBSCRIBED」表示や「🔄再読み込み」ボタンの記述がありますが、現在のページには無い可能性があります。実機のOBSで一度表示を確認しておくと安心です。

8. 公開・更新のしくみ（変更が学生に届くまで）

このサイトは GitHub Pages で公開されています。仕組みはシンプルです。

　ファイルを直す（Claudeが編集）
　　　↓
　GitHubに保存（コミット＆プッシュ＝Claudeが実行）
　　　↓
　数十秒〜数分で、公開URLに自動反映
　　　↓
　学生がページを再読み込みすると最新の問題が見える
  • 問題を直したり追加したりすると、GitHubに保存された時点で自動的に公開サイトにも反映されます。特別な「アップロード」操作は要りません。
  • 学生側は、ページを再読み込み（リロード）すれば最新になります。
  • 「ちゃんと反映されたかな？」と思ったら、公開URL（…/index.html）を開いて確認できます。

このプロジェクトは main（メイン）という1本の流れに直接保存する運用です。Claudeに「直して」と頼むと、修正 → 保存 → 公開反映まで一通りやってくれます。
